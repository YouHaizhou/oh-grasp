# oh-grasp 分析提示（可移植）

你的任务：读取一个**单个 JavaScript 文件**，产出符合 `schema.json` 的 **JSON IR**（中间表示），供后续校验与渲染。

## 输入

用户指定一个 JS 文件的路径。**只读这一个文件**，不要追着 import / require 去读其它文件。

## 产出：JSON IR

严格按 `schema.json` 的字段产出 JSON，只输出 JSON（可包在一个代码块里，不要带解释文字）。

1. **meta**
   - `title`：文件名（含扩展名）。
   - `subtitle`：一句话说清这个文件是干什么的。
   - `input`：这个文件的输入（数组，可为空）。
   - `output`：这个文件的输出（数组，可为空）。

2. **modules**：把文件拆成模块。
   - **外部模块**：一个 import / require 对应**一个**外部模块，不要合并。`label` 用模块名（如 `react`、`fs`、`./utils`）。`type` = `"external"`。`input` = 从它消费的具名成员（数组，如 `["useState", "useEffect"]`；默认导入或整体引入用 `["default"]`）。`description` = 一句话说明为什么需要它。
   - **内部模块**：文件内的逻辑单元（函数 / 类 / 关键对象）。`label` 用源码里**真实存在的标识符**（函数名/类名），因为校验脚本会检查它是否在源码中存在。`type` = `"internal"`。
     - `description` = 一句话概要（图上显示）。
     - `detail` = 更完整的职责说明（弹窗里显示，比 description 长）。
     - `source` = 该模块的**完整函数体原文**（弹窗里显示，从源文件里原文摘出，含函数体全部内容，不要只给声明行）。
     - `sourceLine` = 该模块定义在源文件中的起始行号（整数，可选，仅展示用）。
     - `group` = 所属分组的 id（可选，指向下面 `groups` 里的 id；不填即单飞叶子）。
   - 每个模块 `id` 唯一，用稳定的小写标识符（如 `ext_react`、`parse_config`）。

3. **groups**（可选）：把共同实现一个功能的内部模块聚成一个分组，让大图变小图。
   - 每个分组：`id`（稳定小写，如 `grp_dispatch`）、`label`（抽象分组名，如「命令分发」，**无需**对应源码标识符）、`description`（一句话说明它做什么）。
   - 每个分组**至少 2 个内部模块成员**；成员通过自己的 `group` 字段指向该分组 id。
   - 不必全部分组：独立工具函数可作为单飞叶子（不填 `group`）。
   - 分组不手写输入/输出摘要——折叠后图的输入/输出由 viewer 从组间连接**推导**，所以**每条真实的组间调用/数据流都必须写成 connection**（漏一条，折叠图上那个分组的输入/输出就少一项）。

4. **connections**：内部模块之间的数据流。每条含 `from`（源 internal 模块 id）、`to`（目标 internal 模块 id）、`label`（流动的数据/含义）。**两端都必须是 internal 模块**。没有数据流可省略该字段。
   - `label` 用短而具体的短语说明流动什么（如 `renderer + args`、`checker receipt`），不要写空泛的 `数据`/`调用`。
   - **写全真实连接**：同一文件里每一处真实的「模块 A 的结果流向模块 B」都要有一条 connection（含跨分组的调用，如某命令处理器 → 公共的 run_node/exit_from 助手）。只写真调用、真数据流，**不要编造**没有的依赖关系。

## 约束

- 不要编造：每个 internal 模块都必须能在源码里找到对应定义（其 `label` 就是那个标识符）。
- 分组 `label` 是抽象概念、无需在源码中存在；但分组的成员必须是源码里真实存在的内部模块。
- `source` 必须从源文件**原文摘出**（可含换行、含完整函数体），不要重写、缩写或只给声明行。
- 一个 import = 一个外部模块。
- 只读这一个文件，不追 import。
