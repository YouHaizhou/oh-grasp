# oh-grasp 分析提示（可移植）

你的任务：读取一个**单个 JavaScript 文件**，产出符合 `schema.json` 的 **JSON IR**（中间表示），供后续校验与渲染。

## 输入

用户指定一个 JS 文件的路径。**只读这一个文件**，不要追着 import / require 去读其它文件。

## 产出：JSON IR

严格按 `schema.json` 的字段产出 JSON，只输出 JSON（可包在一个代码块里，不要带解释文字）。

### 双语：每个散文标量都写成 `{ "zh": …, "en": … }`

**两种语言都必填**，缺一种校验直接硬报错、不出图。写成 `{ "zh": "…", "en": "…" }`，两边都要非空。`zh` 是主要读者的语言，写成通顺的中文；`en` 是同一句话的英文。走这条的字段一共八处：

| 字段 | 是什么 |
|---|---|
| `meta.subtitle` | 一句话说清这个文件是干什么的 |
| `meta.input` 的**每一项** | 这个文件的一项输入 |
| `meta.output` 的**每一项** | 这个文件的一项输出 |
| `group.label` | 分组名 |
| `group.description` | 一句话说明这个分组做什么 |
| `module.description` | 模块的一句话概要（图上显示） |
| `module.detail` | 更完整的职责说明（弹窗里显示，比 description 长）——仅 internal |
| `connection.label` | 这条线上流动的数据 / 含义 |

**名字不译**，永远是普通字符串：`meta.title`（文件名）、`module.label`（internal 模块是源码标识符、external 模块是包名）、以及全部 `id` / `source` / `sourceLine` / `from` / `to` / `group`。译了名字就对不上代码，校验的存在性检查会立刻失效。

1. **meta**
   - `title`：文件名（含扩展名）。**普通字符串**。
   - `subtitle`：一句话说清这个文件是干什么的。`{zh, en}`。
   - `input`：这个文件的输入（数组，可为空；**每一项**都是 `{zh, en}`）。
   - `output`：这个文件的输出（数组，可为空；**每一项**都是 `{zh, en}`）。

2. **modules**：把文件拆成模块。
   - **外部模块**：一个 import / require 对应**一个**外部模块，不要合并。`label` 用模块名（如 `react`、`fs`、`./utils`）。`type` = `"external"`。`input` = 从它消费的具名成员（数组，如 `["useState", "useEffect"]`；默认导入或整体引入用 `["default"]`）。`description` = 一句话说明为什么需要它（`{zh, en}`）。
   - **内部模块**：文件内的逻辑单元（函数 / 类 / 关键对象）。`label` 用源码里**真实存在的标识符**（函数名/类名），因为校验脚本会检查它是否在源码中存在。`type` = `"internal"`。
     - `description` = 一句话概要（图上显示）。`{zh, en}`。
     - `detail` = 更完整的职责说明（弹窗里显示，比 description 长）。`{zh, en}`。
     - `source` = 该模块的**完整函数体原文**（弹窗里显示，从源文件里原文摘出，含函数体全部内容，不要只给声明行）。**普通字符串**。
     - `sourceLine` = 该模块定义在源文件中的起始行号（整数，可选，仅展示用）。
     - `group` = 所属分组的 id（可选，指向下面 `groups` 里的 id；不填即单飞叶子）。**普通字符串**。
     - `uses` = 该模块**直接消费**的 external 模块 id（可选数组，如 `["ext_fs", "ext_path"]`）。只列它**自己直接**用的——下游模块用的不列、不做传递闭包；每一项必须是 **external** 模块的 `id`（external 声明在它后面也合法，不必先声明）。不填＝没有外部依赖。
     - `runtime` = 该模块对宿主运行时的调用（可选数组），每项写**属性路径**（如 `process.exit`、`process.env`、`process.cwd`）——**不带括号、不带参数、不带说明**：`process.exit(1)` 要写成 `process.exit`，裸 `process` 不是一个调用、不要写。不填＝没有宿主调用。
   - 每个模块 `id` 唯一，用稳定的小写标识符（如 `ext_react`、`parse_config`）。

3. **groups**（可选）：把共同实现一个功能的内部模块聚成一个分组，让大图变小图。
   - 每个分组：`id`（稳定小写，如 `grp_dispatch`）、`label`（抽象分组名，如「命令分发」，**无需**对应源码标识符）、`description`（一句话说明它做什么）。`label` 与 `description` 都是 `{zh, en}`。
   - 每个分组**至少 2 个内部模块成员**；成员通过自己的 `group` 字段指向该分组 id。
   - 不必全部分组：独立工具函数可作为单飞叶子（不填 `group`）。
   - 分组不手写输入/输出摘要——折叠后图的输入/输出由 viewer 从组间连接**推导**，所以**每条真实的组间调用/数据流都必须写成 connection**（漏一条，折叠图上那个分组的输入/输出就少一项）。

4. **connections**：内部模块之间的数据流。每条含 `from`、`to`、`label`、`description`。**两端都必须是 internal 模块**。没有数据流可省略该字段。
   - `from` / `to`：源 / 目标 internal 模块 id。**普通字符串**。
   - `label`：`{zh, en}`。中文里写成一句**动宾短语**（如「传入渲染器路径」），它是画布中点显示的那句话。用短而具体的说法说明流动的是什么，不要写空泛的「数据」/「调用」。
   - `description`：**四段说明，中英各一套，八个格子一个都不能空**：

     ```jsonc
     "description": {
       "zh": { "source": "…", "process": "…", "output": "…", "purpose": "…" },
       "en": { "source": "…", "process": "…", "output": "…", "purpose": "…" }
     }
     ```

     - `source`（**从哪来**）：这段数据的上游是什么。
     - `process`（**经过什么处理**）：源模块对它做了什么。
     - `output`（**输出了什么**）：交给下游的是什么。
     - `purpose`（**用于什么**）：下游拿它做什么。

     每个格子**一句话，约 ≤40 字**（是风格要求，不是硬上限——但别写成一段话）。四个字段名固定，**不要改叫** `origin` / `how` / `what` / `why`；`from` 已被 connection 占用表示源模块 id，也不能挪来表示「数据从哪来」。
   - **同一个 `label` 的边复用同一段四段文字**：同一个数据出现在多条边上时，`description` 要逐字相同。同一个词写成两套说法，读者会怀疑它们是不是同一个东西。
   - **写全真实连接**：同一文件里每一处真实的「模块 A 的结果流向模块 B」都要有一条 connection（含跨分组的调用，如某命令处理器 → 公共的 run_node/exit_from 助手）。只写真调用、真数据流，**不要编造**没有的依赖关系。
   - 外部依赖**不进 connections**——它写在消费方模块的 `uses` 里（见上）；`connections` 只画 internal 之间。

## 约束

- 不要编造：每个 internal 模块都必须能在源码里找到对应定义（其 `label` 就是那个标识符）。
- internal 模块须用源码中**真实存在的标识符**做 `label`；校验脚本会逐字检查它在源码里是否存在。
- 分组 `label` 是抽象概念、无需在源码中存在；但分组的成员必须是源码里真实存在的内部模块。
- `source` 必须从源文件**原文摘出**（可含换行、含完整函数体），不要重写、缩写或只给声明行。
- 一个 import = 一个外部模块。
- 只读这一个文件，不追 import。
