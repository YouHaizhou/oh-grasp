🔥 **Round 17** · 8 questions

🧩 **Q1** - **双语字段怎么表示**
- (a) **结构化对象**：每个可译文本字段变成 `{zh, en}`（`description:{zh,en}`、`connection.label:{zh,en}`…），一处规则全适用。
- (b) **并列后缀字段**：`label` + `labelEn`、`description` + `descriptionEn`，老字段不动。
- (c) 双语各存一份 IR / 各出一份 HTML。

💡 推荐 (a)。一条规则贯穿 meta / group / module / connection，viewer 只需一个 `pick(field)` 取值函数。(b) 会让每个字段名翻倍、易漏配。注意：**internal 模块的 `label` 是源码标识符，不翻译**（validate 要求它在源码中存在）；可译的是 description / detail / group.label / meta 散文 / connection.label / 新增的边四段。

ans：a.

🎯 **Q2** - **缺语言的回退与校验强度**
- (a) **双语必填**：validate 硬报错，缺任一语言不许出图。
- (b) **至少一种**必填，缺另一种则切换时回退显示已有语言并标注。
- (c) 只 warn，不阻断。

💡 推荐 (a)。你反馈 2/4 的病根就是「中英混杂看不懂」；(b) 的静默回退会把混杂原样放回来。代价是生成字量上升——但这个代价正是「两种版本都好看」的票价。

ans：a.

🧩 **Q3** - **边四段说明的结构**
- (a) **固定四字段**各一句：`source`（从哪来）/ `process`（经过什么处理）/ `output`（输出了什么）/ `purpose`（用于做什么），双语各一套。
- (b) 一段自由文本（≤ N 字），双语各一段。
- (c) 两段：做什么 + 用途。

💡 推荐 (a)。四段一一对应你原话的四个问题，结构固定后弹窗排版稳定、双语能逐段对齐；自由文本会让不同边的说明长短不一、点开形状不齐。

ans：a.

🎯 **Q4** - **四段说明写在哪一级、聚合边怎么展开**
顶层 14 条是**多条 connection 折成一条**（如 `arg_parse→render` 折了 6 条），底层 47 条才是原子。
- (a) **每条 connection 都写四段**（双子语）；顶层聚合边点开 = **列出其下各 connection 的四段清单**。
- (b) 只给顶层聚合边写一份「合并叙述」的四段。
- (c) 全部只给一句短语，四段省略。

💡 推荐 (a)。原子写在 connection 上，任何出现位置（顶层、子图、端口清单）点开都一致；(b) 的合并叙述要凭空概括 6 条边，正是「模型猜、边是真」的老病（ADR-0006 的教训）。成本是 archify 47×2 语言的四段，是这轮最大的一笔生成开销。

ans：a.

👀 **Q5** - **交互模型统一**
现在点节点 → 详情/子图；点端口 → 连接清单；本轮新增点边 → 四段说明。三种触发三套面板，容易各长各的。
- (a) **统一成一个弹窗组件**（标题 + 分节），三种触发共用；点边的命中区 = **整条路径 + 中点标签**；hover 只给轻提示（不承担内容）。
- (b) 边详情用**悬停浮层**，不弹窗。
- (c) 边详情**并入节点弹窗**（不单独弹）。

💡 推荐 (a)。一个组件三种入口，样式与关闭行为一致；(b) 的浮层放不下四段双语；(c) 点边却弹节点会让「我点的是这条线」的心智断裂。

ans：a.

⚖️ **Q6** - **虚节点路由的形态**
- (a) **正交折线**：直角拐弯，逐层从盒间空隙竖直穿下。
- (b) **平滑曲线**穿过空隙。
- (c) 折线 + 圆角过渡。

💡 推荐 (a)。正交线与「反馈弧绕侧」的直角色调一致，读者能一眼跟上「这条边在第几层掉了头」；虚节点也**参与 barycenter 排序**，顺带压交叉。允许边与边交叉，只保证不穿盒。

ans：a.

🧩 **Q7** - **端口内容口径的细节**（Q7 的推论）
- (a) 去重按**语义文本**（当前语言下同文本即同一内容），端口旁代表内容取 **IR 顺序第一条**（稳定可预期）；**外部依赖不占端口**，只在弹窗第二段列。
- (b) 端口合并显示 `×N（组间）· ×M（外部）`。
- (c) 端口只给计数，不给代表内容。

💡 推荐 (a)。端口继续只表达「组间边」这一个事实源（ADR-0006 不破）；外部依赖另开一段（Q8），两者不混在一个数字里。代表内容取第一条——顺序稳定，读者扫图时不会因为去重算法改动而看到不同的词。

ans：a.

🧩 **Q8** - **「成员直连外部」的数据从哪来**（Q8 的前提，事实核查已回来）

查清楚了，**现在没有任何数据源**：

- `connections` **只允许 internal↔internal** —— validate.js 第 139–147 行硬拒 external 端点（`'from' must reference an internal module, got 'ext_fs'`）。实排下来 boundary connection = **0 条**。
- 41 个 internal 模块的字段集完全一致：`[id, label, type, description, detail, source, sourceLine, group]`。**没有 `input`，没有 `output`，没有任何 `uses` 字段**。
- 14 个 external 模块只带自己的 `input`（被导入的**符号名**，如 `["spawnSync"]`、`["default"]`），**不记录谁用了它**；它们的 description 里也没有任何 internal 模块 id（已逐条程序化核对）。
- 唯一残留信号是 `source` 里的自由文本。所以按原样实现，`grp_arg_parse` 的第二段会是**空列表** —— 四个成员在结构化字段里一个外部信号都没有。

- (a) **新增 `module.uses`**：internal 模块上加一个数组，列它直接消费的 external 模块 id（如 `["ext_path","ext_fs"]`）；validate 校验 id 存在且必须是 external。弹窗第二段 = 按 group 聚合成员的这个字段。
- (b) **放宽 `connections` 允许 external 端点**：这类边只在弹窗列表里出现，不画进图。
- (c) **不新增结构**：第二段不显示（Q8 降级为「只列组间边」）。

💡 推荐 (a)。这是**消费关系**，不是数据流边 —— 挂在最靠近事实的地方（成员自己），一个成员一行，模型生成 IR 时正在逐字读源码、填这个字段几乎零额外成本；也和 ADR-0006「外部依赖走侧栏、不进数据流」不冲突。(b) 会把两种语义不同的东西塞进同一个数组，validate 的 `internalIds` 检查要开洞，viewer 到处要判「这条边画不画」，是 ADR-0006 边界的一次松动。(c) 诚实但等于没答你的反馈 6。

注意：无论选哪个，**41 个 internal 模块都要过一遍源码**才能填准，(a) 的代价主要在这里，不在 schema。

ans：a.
