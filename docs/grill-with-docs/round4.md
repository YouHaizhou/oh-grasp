 Q1 — 第一版针对哪种语言的代码文件

  「单文件」的分析（外部依赖 / 内部模块 / 输入输出）是语言相关的——Python 的 import、Go 的 package、JS 的 require/export
  结构不同，「存在性校验」判「内部模块真存在」的规则也随语言变。第一版先支持哪一种？
  - (a) Python：结构最规整（import/def/class 边界清晰），「外部依赖/内部模块/输入输出」的界定最明确，校验脚本最易落地；
  - (b) JavaScript/TypeScript；
  - (c) Go / Java / 其他；
  - (d) 语言无关的弱分析：不按语法解析，只让模型凭文件内容自己判断（最通用，但校验最弱、存在性检查做不了）。
ans：先做js的，另外对于非代码文件后续也要处理，目前的内容是为了后面做项目文件图，已生成的代码文件图+非代码文件就构成项目文件图了，还会有图内容的排版，不过都是后面的内容了

  ⚖️  Q2 — 输出的形态：纯 Mermaid 图 vs 图 + 结构化头部

  你列了 6 样：外部依赖、内部模块、组合方式、输入、输出、文件作用。前 3 样是图（节点和边），后 3 样（输入/输出/作用）更像注释/元数据。输出是：
  - (a) 纯 Mermaid 图，把输入/输出/作用也硬塞进节点或标签里；
  - (b) Mermaid 图 + 图上方一小段结构化文字（作用、输入、输出），Mermaid 只专注画「模块 + 依赖 + 组合」；
  - (c) 其他。
ans：最终输出形态考虑html的图，mermaid图可以作为中间产物，产物形式类似于template里的，不过这个是项目的架构图。

  🎯 Q3 — 分析范围：只读这一个文件，还是追 import

  「依赖哪些外部模块」——分析时只看这一个文件自身（把 import 到的模块名列出来即可，不打开那些模块），还是顺着 import 追进项目里其他文件去看？
ans：外部import，一个import算成一个外部模块，输入是什么，模块描述，这些内容就可以了。文件内部做模块划分，模块间的数据流动，模块描述这些内容。
