诊断（facts，我的活）

  这是 round6 Q1 选项 (b) 的正式展开——分组是「语义分组」：哪些函数共同实现一个功能，只有模型知道，所以是**分析侧改动**，动 prompt + schema + validate + viewer 全链路，比上一轮「只修 viewer + 数据契约」大。

  几个必须先摆平的事实：

  1. 现 IR 是**平铺**的：`modules[]`（type 只有 external/internal）+ `connections[]`。没有「容器」概念。分组要么给 internal 模块加引用，要么引入容器实体，要么改 type 枚举——三种 schema 形状，改动面差别很大。
  2. 「label = 真实标识符」的存在性校验是核心不变量（validate.js 的 `identifierExists`）。分组名是**抽象概念**（如「命令分发」），源码里没有这个标识符——必须为 group 单独放宽这条，否则校验必挂。放宽时「不编造」原则怎么守住，要单独定。
  3. 分组能砍顶层节点数（41 → 若干 group+叶子），认知负担骤降。但它**不能消除连线交叉**：group 内部仍是子图、group 之间/group 与叶子的边仍会交叉。它做的是把交叉「关进盒子里」，别让不同功能的线搅在一起。这点要对齐预期，别当成交叉最小化的替代品。
  4. 「一进一出」是你的直觉模型，但真实 group 常有多条进出边（一个功能可能消费多个外部模块、输出到多处）。字面「一进一出」要求模型强抽象，有编造风险。

  🔥 Round 1 · 4 questions

  🎯 Q1 - 分组的 IR 数据模型（根决策）
  group 在 JSON IR 里怎么表示？这决定 schema/validate/viewer 的改动形状。
  - (a) 平铺 + 分组引用：internal 模块加可选 `group` 字段，顶层新增 `groups:[{id,label,description}]`。模块仍平铺，group 只是索引。schema 改动最小，validate/viewer 都好改，深度自然固定 1 层。
  - (b) 嵌套树：group 是容器，内部直接嵌 members，可递归嵌套。表达力强，但 schema/validate/viewer 全要改成递归遍历，复杂度和出错面都大。
  - (c) group 作 type：`type:"group"` 与 external/internal 并列塞进 `modules[]`，带 `members:[id]`。跟 (a) 目标一致，但会跟「module 必须有 label/description/source」的现有校验打架，还得特判。
  💡 推荐 (a)。你的诉求是「大图变小图 + 钻取」，一层的 group-ref 就够；嵌套树是过度设计，等真出现「group 里还有 group」再升级。深度固定 1 层，问题少一半。
ans：a。

  🧩 Q2 - group 的 label 语义（存在性校验怎么放宽）
  group 名是抽象概念（「命令分发」），源码里没有这个标识符，必须绕过 `identifierExists`。放宽到什么程度？
  - (a) 完全自由：group 的 label/description 由模型自由命名，只校验「非空 + 成员引用有效 + 成员必须 internal」。守住「成员都得真存在」这条底线。
  - (b) 也要锚定源码：group 名必须也是真实标识符（如用某代表函数名）。保住「label=真实标识符」不变量，但抽象的「命令分发」这类名字就没了，分组失去语义表达力。
  - (c) 自由 + 最少成员约束：在 (a) 基础上要求每个 group 至少 2 个成员（防空壳/单成员分组——单成员分组不减节点数，纯增层级）。
  💡 推荐 (c)。group 名自由是分组的意义所在；(b) 砍掉语义。而「至少 2 成员」是便宜的防空壳约束，顺手挡住「给每个函数套个壳」这种作弊。编造防线 = 成员必须真实存在，这条保住。
ans：c。

  ⚖️ Q3 - group 对外接口：字面「一进一出」还是边界边
  折叠后，group 对外暴露什么线？
  - (a) 边界边：只保留跨 group 边界的边（连到 group 外的 from/to），隐藏内部边。忠实、零编造，但一个 group 可能仍有多条进出线。
  - (b) 字面一进一出：模型为每个 group 抽象唯一「输入」「输出」标签。视觉最简（正是你描述的样子），但真实功能常多进多出，强抽象有编造风险、丢信息。
  - (c) 边界边 + 可选摘要：以 (a) 为底，模型可额外给 group 一个 `input`/`output` 摘要字段，图上显示摘要、细节钻取时看边界边。
  💡 推荐 (a) 起步。先忠实呈现边界边（零编造、实现最简），跑通后再按需加摘要层。直接上 (b) 的「一进一出」会把「语义压缩」和「不编造」顶死，是这轮风险最高的一个点。
ans：c，这里补充下，多条输入边汇聚到一个输入点，不过同样支持点击输入点看具体有哪些输入。

  🧩 Q4 - 钻取交互：点 group 怎么看内部
  叶子模块点开仍是「函数介绍 + 源码」（现有弹窗），group 点开要展示内部关系，怎么呈现？
  - (a) 复用弹窗：点 group 弹 modal，内部渲染该 group 的迷你 flow 图（成员 + 内部边 + 边界边）。group 弹「子图」，叶子弹「详情+源码」，两种弹窗分流。
  - (b) 就地展开：group 节点在图上原位展开成子图，推挤兄弟节点。直观但布局重算复杂，易跳变。
  - (c) 导航跳转：点 group 切到「只看该 group」的独立视图/路由，返回按钮退出。
  💡 推荐 (a)。现有 `detailOverlay` + `renderA` 的 flow 渲染逻辑可复用，只是把「单模块 detail+source」和「group 子图」两条分支接进同一个弹窗。最小增量，不动已有缩放/平移/双击复位。
ans：a
