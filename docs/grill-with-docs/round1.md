Q1 — 这个「项目」的主体到底是什么（根决策）

  「做一个项目」可以是三种东西，它决定整个 repo 的骨架：
  - (a) 一套可移植的增强服务格式/规范 —— 任何人按格式写一个增强，就能装进 codex/dsh 等任意平台；
  - (b) 一批具体的增强服务 —— 先做几个真正有用的能力；
  - (c) 两者都要 —— 格式 + 第一批示范服务。
ans: b，这个项目是为了实现一种增强服务，不是规范，不过适配主流agent平台

  ⚖️  Q2 — 单个增强服务的交付形态（全项目最核心的权衡，即之前问的第 4 条）

  一个「增强服务」落到平台上，物理形态是：
  - (a) 纯技能包：一段 prompt/指令 + 可选标准库脚本，靠平台原生机制加载。最轻、真零依赖、最大复用平台模型，但能力受限于「模型 + 平台已有工具」；
  - (b) 可执行工具：agent 经 MCP 或子进程调用真程序。能做模型做不到的事（如真渲染出图），但要运行时 + 协议，牺牲零依赖；
  - (c) 每平台原生插件：DSH 插件 + Codex 插件各写一份。最地道最强，但 N 份实现，牺牲「轻量/可移植」；
  - (d) 可移植格式 + 每平台薄适配器：格式是核心，适配器把同一份技能映射到各平台原生机制。
ans：a + d，不过会需要一些脚本文件来检验模型输出，给模型提供标准优化这种代码文件

  ⚖️  Q3 — 「零依赖」的精确边界

  「装了不装别的」可以有三档：
  - (a) 零第三方包，但可用平台/机器自带的 Node 或 Python 标准库；
  - (b) 连运行时都不假设——增强必须是纯文本（prompt + 数据），一行可执行代码都没有；
  - (c) 允许自带一个极小单文件运行时。
ans：a
