诊断（facts，我的活）

  你这个提醒是对的。我 round12 的 Q2 答案是「label + 整句 description + 推导端口，删 badge」——这确实只是在修 archify 这张卡挤的问题（5 行塞 96px、摘要和边对不上），不是一套对所有输入都成立的排版模型。真正的通用问题是：**一个节点的盒子，在内容（名字/描述长度、成员数、I/O 边条数）任意变化时，该怎么定尺寸、放什么、怎么表达 I/O**。

  把「通用」拆成三层，逐层看：

  1. **I/O 已经从「一句话」变成「推导出的边列表」（N 条）**。这是根变化：一句话摘要可以塞进固定盒子，但 N 条边塞不进任何固定盒子。所以「怎么在盒子上表达一个任意长度的 I/O 列表」才是排版的核心，而不是「盒子做多高」。
  2. **I/O 一旦不占盒子，盒子只剩「身份 + 作用」**：名字（identifier/组名）+ 一句描述。这俩都是短文本，尺寸问题自然消解（描述封顶 1~2 行 + 省略号）。
  3. **宏布局（画布级分层算法）是另一码事**：archify 有循环（cli_core↔render）和孤岛（misc_commands），分层 fallback 摆得乱，但这是「图整体怎么摆」的问题，和「卡片长什么样」不是同一层。

  所以这轮把排版从「卡片级」往上抬一层，定三个通用原则。round12-Q2 的答案作废，由这轮取代。

  🔥 Round 3 · 3 questions（排版通用化）

  🎯 Q1 - 推导出的 I/O 怎么表达（根决策）
  I/O 现在是「边列表」（N 条，可为 0 可为 50）。在盒子上怎么表达一个任意长度的列表？
  - (a) 端口为中心：盒体只有「名字 + 描述」；上/下端口各是一个点，端口上标「×N」（入/出边条数），悬停或点击看清单。盒体永不因 I/O 变大，N=0/1/50 都成立。
  - (b) 盒内 chips：每条边一个小标签叠在盒上/下沿。一眼全见，但 N 大盒体暴涨、N 小空白。
  - (c) 计数摘要行：盒内一行「3 入 · 2 出」，端口点开看明细。比 (a) 多一句「3 入」，但仍没说流入啥。
  💡 推荐 (a)。端口本来就是 ADR-0005 定的「多条入边汇聚到一个输入点」的抽象，它天生为 N 条边而设；I/O 交给端口 = 盒子永远紧凑、对任何边数都成立，正是「通用」要的。盒内不再重复列 I/O，只留身份 + 作用。
ans:a.

  🧩 Q2 - 盒体解剖与尺寸（Q1 的推论）
  一旦 I/O 交给端口，盒子只剩「名字 + 一句描述」。尺寸怎么定？
  - (a) 固定盒 + 描述封顶：名字 1 行、描述最多 2 行（超长省略号、完整版进弹窗），盒高基本恒定。分层布局最省心、无挤（挤是之前 5 行塞出来的，现在只剩 2~3 行）。
  - (b) 高随内容：描述不封顶、盒子无限长高。诚实但长描述（几十字）会把图撑得稀烂，分层 pitch 要按层内最高算。
  - (c) 极简：盒里只名字，描述也点开才看。最可扩展，但丢了「一眼看到作用」——这是本工具的核心认知价值。
  💡 推荐 (a)。认知价值在「一眼看到作用」，(c) 把它丢了；而描述封顶 2 行 + 省略号，既保住一览又不失完整（弹窗有全文）。固定盒让分层布局保持简单。
ans:a.

  ⚖️ Q3 - 宏布局（画布级）这轮动不动
  「排版」也可能指整体画布——分层算法、循环 fallback、孤岛摆放、连线交叉。范围怎么定？
  - (a) 只做节点/卡片级通用排版，宏布局维持现状（分层纵向 + 循环 fallback）。
  - (b) 连宏布局一起重做（分层算法选型、循环/孤岛/交叉的系统性处理）。
  💡 推荐 (a)。你这次的痛是「卡片挤 + I/O 看不懂」，不是「图整体摆放乱」；宏布局是独立的大活（分层 vs 力导、循环怎么排），和卡片不是同一层，别混。若宏布局也想要通用方案，另开一轮单独议。
ans:b,宏布局也要处理
