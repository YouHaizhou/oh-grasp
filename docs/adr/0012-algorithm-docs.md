# 算法文档：`docs/algorithms/`，与 ADR 分工

用户要求：「在 docs 里单开一个文件夹用于存储项目使用哪些算法，用于解决什么问题，可以先把目前使用到的算法统计一次。」

这不是一次性的统计，是给项目**立一个文档类别**——所以要先说清它和已有文档的分工，否则 `docs/` 会攒出两份互相矛盾的现状描述。

## 决策一：按问题域分文件，README 做索引

```
docs/algorithms/
├── README.md        索引 + 与 ADR 的分工 + 已知复杂度隐患
├── text.md          中英混排的行宽与截断
├── graph.md         断环 / 分层 / 排序 / 分量 / 装箱 / 聚合
├── geometry.md      连线形状 / 行几何 / 区域堆叠
├── viewport.md      缩放 / 平移 / fit
├── validation.md    引用完整性 / 存在性
└── rendering.md     转义 / 自包含装配 / 双模式
```

按**问题域**而不是「文件/函数」分：读者的问题是「文字怎么量宽」，不是「`viewer.js` 里有什么」。同一件事的算法散在多个函数里时（如 `chW` / `fitWidth` / `lineCap` / `wrap2` / `cutGuard` 都服务于「中英混排的宽度」），域文件把它们收在一起。

README 里有一张 27 行的**一览表**（算法 / 域 / 位置），作为入口。

## 决策二：ADR 记「为什么选」，算法文档记「用了什么」

| | ADR | 算法文档 |
|---|---|---|
| 回答 | 为什么这么选？否掉了哪些方案？ | 用了什么？解决什么问题？复杂度多少？代码在哪？ |
| 时态 | 决策当时 | 当前现状 |
| 变更 | 追加新 ADR，旧的标 supersede | 直接改，跟着代码走 |
| 粒度 | 一条决策一篇 | 一个问题域一篇 |

**同一件事不在两处写两遍。** 布局用「Kahn + 最长路径分层」是算法文档的内容；「为什么不用 Sugiyama 完整实现」是 ADR-0007 的内容。算法文档里遇到需要解释取舍的地方，指一句「见 ADR-000X」，不展开。

## 决策三：只记已落地的，规划中的指向 ADR

`docs/algorithms/` 记的是**代码里真实存在**的算法。规划中或讨论中的（虚节点路由、barycenter 改造等）不进正文，统一收在 README 末尾的「待实现」一节，每条指向对应 ADR。

理由：这份文档的读者是「想改这个地方的人」，他要确认的是**现在跑的是什么**。混进规划会让「读到的」和「跑着的」分不开——而那正是这个项目一路在砍的东西。

## 决策四：行号是快照，以函数名为准

每条算法的「位置」列同时给**函数名和行号**，README 里明说：

> 行号是快照，会随代码变动而漂移——**以函数名为准**。

给行号是因为它省事（能直接跳），但必须标出它的保质期，否则下一次改动之后这份文档就变成「看着很精确的错信息」。

## 副产品：把已知的复杂度隐患登记在案

写这份文档时核对出来的三处，记进 README 的「已知复杂度隐患」一节：

1. **Kahn 的 `Array.shift()` + `indexOf` 兜底**：O(V²)，在当前的图规模（41 个节点）无感，但它是一颗定时炸弹；
2. **barycenter 的 `predsOf` / `succsOf` 每轮重新过滤**：O(V·E·passes)；
3. **`aggregateEdges` 的折叠 bug**（曾导致 `openPort` 失效）。

第 3 条是**已修**的，留着是因为它解释了一段代码为什么长那样。前两条是**未修**的负债，写明「当前规模无感」——不做无谓的优化，但让它可见。

## 已知限制

- 这份文档**不会自动更新**。它是手写的现状快照，代码改动之后需要人（或 agent）跟着改。缓解办法是让它足够短（27 条），改起来不痛苦——一份需要一小时才能改完的文档，两周后就没人改了。
- 它不替代 `CONTEXT.md`。术语解释在 `CONTEXT.md`（如「增强服务」「适配器」），算法实现在这里。
