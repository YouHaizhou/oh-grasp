# internal 模块的语义分组：平铺 + group 引用，而非嵌套树

大文件（如 archify.mjs，41 个内部模块）的流图即使自适应缩放后，认知负担仍高、连线交叉难读。方案是把「共同实现一个功能的内部模块」聚合成一个**分组（group）**，顶层图按分组显示（大图变小图），点分组钻取内部关系。

IR 数据模型采用**平铺 + group 引用**：顶层新增 `groups:[{id,label,description,inputSummary?,outputSummary?}]`，internal 模块加可选 `group` 字段指向分组 id。深度固定 1 层，不做嵌套树——一层已满足「大图变小图 + 钻取」的诉求，嵌套会迫使 schema/validate/viewer 全改成递归遍历，复杂度与出错面都大，等真出现「分组里还有分组」再升级。

两个关键取舍：

1. **分组 label 豁免存在性校验**。原有不变量「internal label = 源码真实标识符」对分组不成立——分组名是抽象概念（如「命令分发」）。防编造的底线改为「成员必须真实存在」+「每个分组至少 2 个成员」（防空壳/单成员分组，单成员分组不减节点数、纯增层级）。

2. **对外接口用边界边 + 端口收敛，而非字面「一进一出」**。真实分组常多进多出，字面一进一出要求模型强抽象、有编造风险。落法：保留所有跨分组边界的连接，多条入边汇聚到分组节点的**输入端口**、出边汇聚到**输出端口**（点端口弹该端口全部边的清单）；模型可额外给分组一句 `inputSummary`/`outputSummary`，显示在端口旁。端口置于节点上下沿（匹配现有的纵向分层布局），而非左右。

未分组叶子允许单飞：工具函数不必硬塞进分组，也让「至少 2 成员」约束有意义（凑不齐就不分组）。
